## Security and operating design for this candidate

The runner is backup infrastructure, never a general PR executor. Use a dedicated non-root service, restricted management access, patched OS, pinned compatible PostgreSQL/Supabase tooling and a reproducible rebuild manifest. Do not add customer payload logs or public diagnostic endpoints. Pin the CLI version: the [November CLI v3 change](https://supabase.com/changelog/supabase-cli-v3) changes local/hosted targeting; review current provider instructions before producing executable backup commands. Follow the [provider-aware restoration guide](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore), with explicit Auth/private-schema/migration coverage rather than assuming CLI defaults include everything.

Propose public-key encryption: runner holds the encryption recipient/public key only; the owner keeps decryption material in approved independent custody with a tested recovery copy. Software key custody has no assumed subscription fee, but actual storage/access and independent reviewer arrangements remain undecided. Use a bucket-scoped upload credential without deletion authority; separate retrieval and retention administration. Review list/read permissions needed for checksum verification rather than calling a broad key write-only. Consider [B2 Object Lock](https://www.backblaze.com/docs/cloud-storage-object-lock) only after retention/cost/cleanup approval: immutable objects cannot be casually removed and can conflict with disposal rules. No lock or policy was configured.

Review a dedicated database backup identity with explicit required schema/table/sequence/catalog permissions, sensitive Auth scope and function-execution restrictions. A cross-tenant backup necessarily contains sensitive data: do not claim it is an application RLS-limited user, reuse application keys, or grant unrestricted bypass without a reviewed necessity. Do not introduce a credential or grant during this planning task. Where provider-supported extraction requires broader access, document that exception and restrict network, runner, secret access and lifetime before approval.

Send a success heartbeat only after a complete consistent export, encrypted upload and integrity verification. A second independent freshness check must detect scheduler stoppage; a timer on the failed runner alone is insufficient. URLs used for heartbeat authentication are secrets. Use explicit bounded timeouts/retries, no overlapping jobs, no fresh-success marking on partial failure. Configure warning at 2h, urgent at 3h and RPO breach beyond 4h from the source snapshot, not the upload timestamp. Test alert delivery/acknowledgement and no-ping detection before relying on this path. Proposed VM capacity, region connectivity/TLS and full restore performance remain untested.

**Operational tradeoff:** this candidate is inexpensive because the owner operates the runner. It adds patching/rebuild/credential responsibilities; it does not solve the unassigned technical backup or unattended weekend failures. Do not provision it until a maintainer and escalation disposition are recorded. If the owner prefers fully managed operation, evaluate another quote rather than presenting this as managed recovery.
